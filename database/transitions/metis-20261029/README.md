# Metis data import — current PHP migrations and MySQL Workbench

The complete executable file is `import-data-full.sql`. It is generated by `build.py` together with its component SQL files. It requires MySQL 8, the current `metis` schema, and the original backup restored into a separate schema named `metis_transition_backup_20261029`. It does not restore the original dump automatically and has not been run against the live application database.

## Current project compatibility

The project uses its 125 PHP migrations and existing DatabaseSeeder. There is no Laravel SQL schema baseline. Both applications share the root PHP migrations. The schema-only JSON snapshot in this folder is an audit/reference artifact, never an automatic migration.

The import preserves all 119 current table definitions, columns, indexes, foreign keys and 125 current migration records. It replaces data in all 118 other target tables, copying the 108 non-migration tables present in the 109-table backup. The source has 2,510,534 rows including 116 old migration records; the 2,510,418 remaining rows are the imported dataset. IDs, timestamps, amounts, statuses, passwords and grants are copied without silent fixes. `leave_balances.balance` is calculated by its unchanged generated-column expression instead of being inserted explicitly. Existing auto-increment counters remain monotonic.

The ten newer tables missing from the backup become empty: business sequences, customer accounts, offices, organization events, shared security mail settings, storefront checkouts and the four two-factor tables. The twelve newer fields remain present with their schema defaults (including storefront visibility false, quantity limits 1/1000, no inclusive-price override and two-factor requirement false). Reconfigure mail, security and storefront access deliberately afterwards. The backup contains 352 permission definitions versus 425 in the current catalog; imported grants are preserved exactly, so newer permissions may require later configuration. Uploaded images/files and APP_KEY are outside the SQL backup; retain them separately. Imported sessions and API/reset tokens also remain as requested. Do not run broad seeders after import because they may change restored data.

## What changed in the complete query

- It works with MySQL Workbench or the mysql CLI and has no SOURCE commands.
- SQL_SAFE_UPDATES is saved, disabled only inside the import procedure, and restored on both success and SQL failure. Do not add manual Safe Updates statements around the file.
- It requires a fresh connection with autocommit enabled.
- Before any deletion, it checks the target/source table inventories, field types, every audited source table's exact row count, and every current PHP migration name. A partially restored backup cannot proceed merely because its tables exist.
- Data replacement is transactional. SQL failures roll back data changes and restore foreign-key checks, SQL mode, time zone and Safe Updates. Failed execution can still advance auto-increment counters, and a failed CALL can leave its helper procedure installed.
- It validates copied row counts and all 200 target foreign keys before commit. Workbench must stop script execution on errors.
- The final 108 verification queries compare all copied values, including generated leave balances. Verification restores the original time zone. These queries run after commit: a nonzero mismatch is an investigation/recovery condition, not an automatic rollback.
- `build.py` reads the audited schema snapshot, not the removed database/schema SQL directory, and regenerates the delivered complete file automatically. `schema-audit.json` fingerprints the current PHP migration sources.

## Before running

Stop both apps, queues, schedulers and integrations that write to the target. Keep the staging schema immutable. Back up current data, deployed APP_KEY and uploaded files; test recovery separately. Reserve sufficient disk space for staging, current data, undo and redo logs. Transactional deletion of millions of indexed audit records may take considerable time. The isolated full-data audit used a 1 GiB InnoDB buffer pool and 512 MiB redo capacity; size the real server for its workload.

If rebuilding the destination for your manual test, run `php artisan migrate:fresh --seed` from `/home/user/metis` BEFORE importing. This command deletes existing tables/data. If the destination already has all current migrations, do not rerun it unnecessarily. ## MySQL Workbench steps

1. Connect to the intended MySQL 8 server. Back up `metis` using Server → Data Export if it contains anything you need. Check the server/connection carefully: the import explicitly targets `metis` regardless of which schema is selected in the sidebar.
2. Restore the original backup through Server → Data Import → Import from Self-Contained File. Select the original backup and a NEW target schema named `metis_transition_backup_20261029`. Do not select `metis`. Confirm import completes with no errors. If staging already exists, inspect it; do not overwrite an unknown database automatically.
3. Run `audit-backup.sql` and confirm all `orphans` results are zero. The complete import also checks all source row counts before deletion.
4. In Edit → Preferences → SQL Editor, increase the DBMS connection read timeout to allow the long transaction (for example 7200 seconds), then reconnect. Enable Query → Stop Script Execution On Errors. Leave autocommit enabled and use a fresh connection without other pending transactions.
5. Open `import-data-full.sql` through File → Open SQL Script. Do not add extra Safe Updates or DELIMITER changes. Choose Query → Execute (All or Selection) with no text selected. Execute the entire file, not only the statement at the cursor.
6. Inspect Action Output. There must be no errors. Each verification result must have target_rows equal to source_rows and mismatched_source_rows equal to zero. Do not rerun the entire import merely to repeat verification; run `verify-data.sql` instead.
7. If an error or disconnect occurs, stop and investigate the server state before retrying. An import error before COMMIT rolls back data; an error in post-commit verification does not undo the committed import. After a failed CALL, remove only the known helper procedure after investigating the cause if CREATE PROCEDURE reports it already exists:

```sql
DROP PROCEDURE `metis`.`metis_replace_backup_20261029`;
```

## mysql CLI alternative

The commands below use a privately configured login path `metis-admin`. Run each command individually, stop on errors, and NEVER use `--force`.

```bash
umask 077
mysqldump --login-path=metis-admin --single-transaction --routines --triggers --events --hex-blob --no-tablespaces --set-gtid-purged=OFF metis > /home/user/dumps/metis-before-transition.sql
mysql --login-path=metis-admin -e 'CREATE DATABASE `metis_transition_backup_20261029` CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;'
mysql --login-path=metis-admin --max-allowed-packet=256M metis_transition_backup_20261029 < /home/user/dumps/metis120261029.sql
mysql --login-path=metis-admin --batch --skip-column-names < /home/user/metis/database/transitions/metis-20261029/audit-backup.sql
mysql --login-path=metis-admin --show-warnings metis < /home/user/metis/database/transitions/metis-20261029/import-data-full.sql
```

## After successful verification

Clear both applications' permission caches and application caches, then test the restored data before reopening the apps or starting workers. Cache clearing intentionally removes transient imported cache entries; it does not change business records.

```bash
cd /home/user/metis
php artisan permission:cache-reset
php artisan cache:clear
php artisan migrate:status
cd /home/user/metis/storefront
php artisan permission:cache-reset
php artisan cache:clear
```

Review login, roles/grants, state context, orders, inventory, payments, product visibility and images. Empty business sequences initialize order counters from existing order numbers through the current application logic. Preserve staging and recovery backups privately until verification is accepted.
