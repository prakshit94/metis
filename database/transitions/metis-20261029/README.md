## What changed in the complete query

- It works with MySQL Workbench or the mysql CLI and has no SOURCE commands.
- SQL_SAFE_UPDATES is saved, disabled only inside the import procedure, and restored on both success and SQL failure. Do not add manual Safe Updates statements around the file.
- It requires a fresh connection with autocommit enabled.
- Before any deletion, it checks the target/source table inventories, field types, every audited source table's exact row count, and every current PHP migration name. A partially restored backup cannot proceed merely because its tables exist.
- Data replacement is transactional. SQL failures roll back data changes and restore foreign-key checks, SQL mode, time zone and Safe Updates. Failed execution can still advance auto-increment counters, and a failed CALL can leave its helper procedure installed.
- It validates copied row counts and all 200 target foreign keys before commit. Workbench must stop script execution on errors.
- The final 108 verification queries compare all copied values, including generated leave balances. Verification restores the original time zone. These queries run after commit: a nonzero mismatch is an investigation/recovery condition, not an automatic rollback.
- `build.py` reads the audited schema snapshot, not the removed database/schema SQL directory, and regenerates the delivered complete file automatically. `schema-audit.json` fingerprints the current PHP migration sources.

## MySQL Workbench steps

1. Connect to the intended MySQL 8 server. Back up `metis` using Server → Data Export if it contains anything you need. Check the server/connection carefully: the import explicitly targets `metis` regardless of which schema is selected in the sidebar.
2. Restore the original backup through Server → Data Import → Import from Self-Contained File. Select the original backup and a NEW target schema named `metis_transition_backup_20261029_143950`. Do not select `metis`. Confirm import completes with no errors. If staging already exists, inspect it; do not overwrite an unknown database automatically.
3. Run `audit-backup.sql` and confirm all `orphans` results are zero. The complete import also checks all source row counts before deletion.
4. In Edit → Preferences → SQL Editor, increase the DBMS connection read timeout to allow the long transaction (for example 7200 seconds), then reconnect. Enable Query → Stop Script Execution On Errors. Leave autocommit enabled and use a fresh connection without other pending transactions.
5. Open `import-data-full.sql` through File → Open SQL Script. Do not add extra Safe Updates or DELIMITER changes. Choose Query → Execute (All or Selection) with no text selected. Execute the entire file, not only the statement at the cursor.
6. Inspect Action Output. There must be no errors. Each verification result must have target_rows equal to source_rows and mismatched_source_rows equal to zero. Do not rerun the entire import merely to repeat verification; run `verify-data.sql` instead.
7. If an error or disconnect occurs, stop and investigate the server state before retrying. An import error before COMMIT rolls back data; an error in post-commit verification does not undo the committed import. After a failed CALL, remove only the known helper procedure after investigating the cause if CREATE PROCEDURE reports it already exists:

```sql
DROP PROCEDURE `metis`.`metis_replace_backup_20261029_bffdf974`;
```
